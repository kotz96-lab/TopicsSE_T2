## Slide 4 — Dataset (~45s)

**Screenshot (required):** the dataset table on our HTML site
(section id `dataset`), scrolled to show a few rows.

**Overlay bullets:**
- 30 HumanEval methods; 1 mutant each
- 10+ pytest tests per method
- 9 mutation categories: boundary, operator, off-by-one, wrong constant,
  logical, invert, wrong variable, deleted check, wrong slice
- **Invariants enforced automatically**: original passes all tests, mutant
  fails ≥1

**Voiceover:**
> The benchmark is 30 HumanEval methods, one mutation each, at least ten
> pytest tests per method. Mutations are spread across nine categories
> — things like flipping a less-than to less-or-equal, subtracting
> instead of adding, off-by-one on a range bound, deleting a guard
> condition. Every mutant is generated by a script that immediately
> verifies two invariants: the original passes all tests, the buggy
> version fails at least one. If either invariant fails, the task is
> rejected. So the ground-truth line is guaranteed to be a real bug the
> tests can detect.

## Slide 7 — SBFL: Tarantula (~45s)

**Screenshot (required):** one entry from `results/sbfl/{task}.json` —
show the passing_tests / failing_tests / ranking structure.

**Also show:** the `has_close_elements` numbered code with lines 6, 7
highlighted (the mutated comparison line + the return-true line).

**Voiceover:**
> Before we ever call an LLM, we run each task's tests with per-test
> coverage. For each executable line we count how many failing tests
> and how many passing tests execute it, and compute a Tarantula
> suspicion score. Higher score means the line is executed more by
> failing tests and less by passing tests, so it's more likely to be
> the bug. Sample from our benchmark shows an interesting failure mode
> though: for `has_close_elements`, Tarantula ranks the `return True`
> line as most suspicious, above the actual `<= threshold` comparison
> on line 6. This becomes important later.

## Slide 13 — Why SBFL hurts (~50s)

**Screenshot:** a qualitative example from the site tagged **"SBFL misled
the model"**, ideally paired with the Tarantula ranking for that same
task.

**Overlay:**
- Tarantula often ranks *symptom* lines (like `return True`) above the
  root-cause line
- LLM anchors on the top-ranked suggestion
- Combining tests + SBFL doesn't rescue — cond D matches C

**Voiceover:**
> The SBFL negative effect held across all three models, so it's not a
> ceiling artifact. The qualitative examples explain why. Tarantula
> frequently ranks *symptom* lines — like a `return True` inside an
> if-branch — as more suspicious than the actual buggy comparison,
> because the return line is only ever executed by failing tests
> whereas the comparison line is executed by everyone who enters the
> branch. When the LLM sees a ranking with "line 7: 0.69" at the top,
> it tends to anchor on it and return line 7 as top-1, even when the
> real bug is line 6. Combining tests plus SBFL doesn't rescue this —
> condition D roughly matches condition C.

## Slide 15 — Threats to validity (~35s)

**On screen:**
- Benchmark is HumanEval — memorized by modern LLMs; may not generalize
- Ceiling effect on the strongest model
- Single-line mutations — real bugs are messier
- Small n per bin (30) → 3–7pp gaps could be noise
- Single prompt template per condition — didn't sweep

**Voiceover:**
> Threats to validity are honest. HumanEval is a known benchmark — the
> models have probably seen these problems during training, so
> accuracies here may be optimistic compared to novel code. The
> strongest model was at the ceiling on cond A, so we can't observe
> "extra info helps" for it. Single-line mutations aren't a fair
> representation of real bugs. Each condition has only 30 samples per
> model, so differences under about 7 percentage points are within one
> standard error of the mean. And we ran a single prompt template per
> condition — a different phrasing might tell a different story.
